## Why

Paul wants to queue Agent Runner evaluation variations and return to results without manually starting and supervising each run. The existing `and-scene` suite already executes an Agent Runner workflow in Docker and produces evaluation evidence. What is missing is the layer that accepts queued requests, schedules them, records progress, recovers interrupted work, and reports outcomes in one place.

The Codagent GitHub Project will also provide a shared view of work across Codagent repositories. Iteration 1 connects that board to the existing evaluation suite through a single local worker. It establishes the operational foundation for later factory work while delivering a useful evaluation service on its own.

The recommendation is **go with caveats**: reuse the suite rather than build another evaluator, preserve its distinction between automated results and an official human-reviewed verdict, and make interrupted execution and reporting recoverable from the first iteration. Manual suite invocation remains useful for setup and diagnosis, but does not provide queue management or unattended recovery. A hosted database or additional orchestration platform adds operational dependencies without addressing a current need for this single-worker slice.

Success means Paul can create an evaluation request from a regular GitHub issue template and later find either traceable per-repetition results ready for human review or an explained deferral with completed work preserved. Creating the request automatically routes it to the factory; no separate manual assignment or move to Ready is required. An automatic interruption must not silently change the requested evaluation or repeat completed repetitions.

## Capabilities

### New Capabilities

- `factory-eval-intake`: Create eval requests through a regular GitHub template, route them automatically using shared configured rules, read issue configuration, select eligible eval work in manual queue order, freeze inputs, and distinguish continuation from an explicit fresh request.
- `factory-claim-lifecycle`: Persist claims and attempts, reconcile board intent with execution evidence, prevent duplicate dispatch, supervise runtime, and recover interrupted work within bounded retry limits.
- `factory-eval-execution`: Invoke the existing `and-scene` suite against clean pinned worktrees with configured role profiles and repetitions, preserving provenance and resumable evidence.
- `factory-eval-reporting`: Interpret suite outcomes, report per-repetition results and deferrals, and reliably hand completed work back for human review.
- `factory-operations`: Configure and diagnose the local service, enforce admission and pause controls, expose status, and document board and Mac mini setup.

### Modified Capabilities

None. This repository contains scaffolding and has no existing capability specifications. The regular issue template and small caller workflow are companion changes in `agent-evals`; routing rules, routing implementation, and the shared workflow live in `agent-factory`. The existing evaluation suite remains the execution interface.

## Technical Approach

Use the scaffolded Python 3.12 project with `asyncio`, `uv`, SQLite, and TOML. Keep the controller deterministic: it runs no LLM step of its own. A polling loop reconciles work and board updates while a separate supervisor manages the active suite subprocess. A single-instance guard prevents the service and a manual invocation from dispatching simultaneously while keeping status and pause controls usable. `agent-factory pause` prevents new execution while allowing the current repetition to finish; `agent-factory resume` permits eligible execution within the admission window. These controls apply to the whole factory and do not introduce Project statuses.

Use a small work-kind boundary for request parsing, execution behavior, and result details. Generic claim/run persistence and lifecycle supervision do not interpret eval blocks, component names, scores, or rubric thresholds. The eval handler owns repetitions and uses a suite integration for `and-scene` commands, readiness, provenance, and outcome interpretation. Reliable issue-comment and field delivery stays generic while the work kind supplies report content. Keep GitHub identities and logical-state-to-field mappings in TOML; the controller must not require the literal organization Codagent-AI, the Project name Codagent, or column names Ready and Review. Continue to support GitHub Projects, SQLite, a single worker, and the Mac launchd deployment in this iteration.

`doctor` diagnoses readiness and explains required operator actions. `status` shows current work and repetition progress, pause state, blocking conditions, and the next permitted start time. `tick` performs one normal polling cycle immediately and may start eligible work; it is not a preview or a bypass of admission controls. A long-running evaluation does not block subsequent service polls. Supply installation and service-management documentation covering explicit executable and credential paths, Docker startup, and preventing idle sleep.

The GitHub template sets native issue Type and applies the request label at creation. Its fenced `eval` block uses TOML, matching the factory configuration format. A small repository workflow calls the shared workflow in `agent-factory`, which invokes the common routing implementation with its configured rules and author-permission check. Those rules supply the destination Project and initial fields. The routing implementation can run on a GitHub Actions runner without the Mac mini service or its SQLite database. There is one implementation of routing behavior; adding a request kind or source repository reuses it through configuration and a caller workflow rather than copying its logic.

Routing adds the issue if needed and initializes its fields once; rerunning delivery must not reset work already in progress or overwrite later human changes. It works while the Mac mini is offline, outside the execution admission window, and while factory execution is paused. The Mac mini's five-minute poll consumes and reconciles the already-routed Project queue. It chooses the first eligible eval in manual Project order, matching the unsorted Ready column in the Eval horizontal group. Implement only the eval execution handler in iteration 1; shared routing does not require implementing future work kinds.

The factory validates execution settings after recognizing an explicitly assigned request; routing does not depend on a valid eval block. Invalid settings receive a red `needs-input` label and a corrective comment, without repeating the same comment every poll. Correcting the eval block clears that label automatically; merely removing the label does not make invalid settings executable. Request labels, Project configuration, and the controller's required GitHub permissions are included in setup.

GitHub owns intent and human handoff; SQLite records what the factory accepted and attempted; suite artifacts own evaluation evidence. The local model uses three tables:

- `claim`: One accepted request with its issue and project-item identity, kind, frozen kind-specific spec JSON, lifecycle state, and outcome. Iteration 1 supports only kind `eval`.
- `run`: One repetition attempt under a claim, with process/container identity, timers, exit classification, evidence location, and recorded results. Supervision fields are common; eval-specific results do not define the generic lifecycle.
- `settings`: Persisted operational controls and discovered board metadata, including pause and admission holds.

Automatic deferral keeps the claim and frozen inputs intact. A card in `Ready` with `Verdict=quota-deferred` or `infra-error` continues its existing claim when eligible. On an otherwise eligible Ready card, a human clearing Verdict or changing the parsed eval settings requests a fresh claim; formatting changes and edits to surrounding prose do not. Reconciliation uses persisted claim and reporting state alongside board observations: a missing Verdict because a factory update has not completed is not evidence of a human reset. The intake specification must define how those observations distinguish continuation from a deliberate fresh request. An edit during execution never changes the running claim's frozen inputs or launches overlapping work.

Allow one automatic recovery retry per repetition, using the suite's supported resume path. Persist the consumed retry budget across restarts and card moves. Waiting for quota does not consume this failure-retry budget; the run history still records execution attempts. If that recovery retry fails, stop the claim without starting its remaining repetitions, preserve completed results and failure evidence, and move the issue to Review with `infra-error` and an explanation. Other eligible requests may proceed. Another evaluation requires an explicit fresh request and starts the requested repetitions anew; completed results from the prior claim remain available. A completed evaluation that finds poor product quality does not trigger a technical recovery retry. A persistent infrastructure problem must remain visible rather than trigger an unbounded execution loop.

On a Codex rate limit, including during product judging, preserve the claim's progress and persist an admission hold until the CLI's reported reset time. Detect these limits only from recognized Codex rate-limit diagnostics in available suite evidence and persisted logs. A generic error or the absence of a reset time does not establish a rate limit and follows ordinary failure recovery. Only after recognizing a Codex rate limit, if the reset time is absent or cannot be interpreted reliably, use a configurable fallback of five hours from detection. Once the hold expires, resume eligible work if the 00:00–15:00 admission window is open; otherwise wait for the next window. The suite continues to manage Claude quota waiting internally. This requires a durable hold in `settings`, not a general provider cooldown subsystem.

Evaluation requests may select Agent Runner and Agent Skills branches, tags, or commits. Resolve those requested refs to immutable revisions and materialize factory-owned clean Git worktrees. `agent-evals` is the tool running the evaluation, not another component whose revision the request varies: use the full harness commit SHA explicitly selected in deployment configuration and retain it in a pinned worktree so repetitions and recovery use the same test code. Recording that version is execution provenance, not evaluation of the harness itself. Retain these pinned worktrees for the lifetime of the claim, including deferrals, and never repoint them for another claim. Invoke `evals/agent-runner/and-scene/run.sh` from the retained `agent-evals` worktree, passing the pinned Runner and Skills worktrees. This provides straightforward isolation now and a basis for later concurrency; iteration 1 still executes one evaluation at a time. The Mac runs the controller and supervisor; the existing suite creates one Docker container per repetition attempt. Include the small suite-wrapper compatibility change needed to mount linked-worktree Git metadata read-only through Runner's existing Docker-argument passthrough, preserving in-container provenance checks.

Record the selected suite identity, the `agent-evals` harness revision, fixture/reference pins, rubric identities, workflow, judge, role settings, and repetitions. Show `Refs` as `runner@<7> skills@<7> evals@<7>`, where each placeholder is the first seven characters of the respective SHA; retain full SHAs in the frozen manifest and its comment. Record the actual container's immutable Docker image ID as observed execution provenance after its build; do not claim its digest was known before the candidate image existed. Preserve score-affecting inputs across repetitions and resume, relying on the suite's provenance checks as well as the controller's records.

Each repetition has a globally distinct, Git-ref-safe suite run identity, including the claim identity in the artifact-directory basename, because the suite also uses it in the candidate branch name. Recovery attempts for that repetition reuse the same identity and suite-owned directory through `--resume` when a valid checkpoint exists. An attempt proven to have stopped before checkpoint creation and candidate execution may retry without that flag using the same identity and bounded retry; corrupt, incompatible, or unexplained missing saved state does not permit a fresh start. Multiple attempt records may therefore reference one directory. Keep controller logs outside suite-owned evidence. The suite continues to own Docker execution, model-auth forwarding, Claude quota waiting, candidate branches/draft PRs, and evaluation artifacts.

Supervise separate inactivity and execution-time limits, initially 30 minutes and six hours, and record distinct outcomes. Measure progress from known suite logs and state artifacts as well as subprocess output; the suite redirects long-running child output into artifact logs. Suspend inactivity detection during a recognized, bounded quota wait and exclude that wait from the execution-time budget. Recognize Claude waits from the pre-wait log message; the suite records its structured wait event only after the sleep returns. Enforce a separate total elapsed-time limit of 12 hours per execution attempt, including quota waits. All three limits are configurable and retain their timing history across factory restarts. Waiting between repetitions for the next admission window does not count toward an attempt's timers.

Launch evaluations so that restarting the factory controller does not terminate an in-progress evaluation. On restart, resume monitoring verified surviving execution without launching a duplicate or consuming a recovery retry. If an evaluation finished while the controller was offline, recover and report its results. Apply the recovery policy only when execution itself stopped unexpectedly; a controller restart alone is not an execution failure.

Reconcile persisted state with process ownership, container identity, and artifacts before retrying. Recover finished-but-unreported results without rerunning the evaluation. Discover the owned container by inspecting its mounts for the repetition's artifact directory as the bind-mount source and `/artifacts` as the destination, then persist its container ID. Recheck ownership before termination; ambiguous matches stop automatic cleanup. A shared Docker image tag alone is insufficient grounds to terminate a container, and no new container-name flag is required. Closing a request's GitHub issue cancels that request: on the next successful GitHub check, stop its owned execution, skip remaining repetitions, and preserve existing evidence. Other eligible requests may continue. GitHub closure automation moves the closed issue's card to Done; cancellation is a user action, not factory-initiated issue closure. For factory-owned requests, reconcile manual Status edits with actual execution: correct an idle request incorrectly marked Running to its appropriate queued or handoff state, and restore Running when verified active work is dragged to Ready, Review, or Done. Continue the same execution; such drags neither cancel it nor create another attempt. Issue closure takes precedence and remains the cancellation gesture. Leave cards without factory ownership alone. Explain corrections through deduplicated issue comments on the normal successful poll and preserve all evidence.

Use `result.json` as the outcome authority when available; an exit code alone does not establish product quality. Preserve execution status separately from product verdict. Once the requested repetitions have settled, any suite-established `product_verdict=fail` or confirmed non-resumable workflow failure makes the board Verdict `failed`; otherwise completed automated evaluation reports `pending-human-review` with the available per-repetition subtotals out of 70. The factory never assigns `passed` in iteration 1. While unfinished work is deferred, the board retains the applicable deferral verdict so it can continue the existing claim; already-established product failures remain visible in the results comment. A suite-established product failure remains distinguishable from a workflow or harness failure, including cases where both product evidence and an execution error exist. Consume the suite's structured failure owner, code, and resumable flag. A confirmed non-resumable implementation-workflow failure settles that repetition as failed without a retry, preserves the suite's product verdict (including unavailable), and allows remaining repetitions to proceed. When all repetitions settle, this workflow failure also yields board Verdict failed with an explanation. Resumable workflow failures and recoverable harness failures retain bounded technical recovery; recognized quota follows its separate hold policy. A workflow-failed status alone does not establish a non-resumable failure. Missing scores or cost data remain unavailable rather than becoming zero. Report each repetition independently so a single board verdict does not hide partial completion or mixed results. Comparative improvement claims and official human-reviewed scoring are outside this iteration.

Use issue comments as an activity history for meaningful request events, including starting work, a technical failure and its retry, waiting for a usage reset, repetition completion, cancellation, and final handoff. Identify the repetition and attempt where relevant and explain what happens next. Routine polls and unchanged waiting states do not produce repeated comments. Each successfully completed repetition awaiting human review includes its own copyable command with safely quoted absolute paths to the retained pinned suite's `human-review.sh` and the actual run directory via `--run-dir`. State that the command runs on the Mac mini holding those paths. Failed or incomplete repetitions receive explanations rather than an instruction presenting them as ready for human review. Human review remains an explicit user action through the existing suite.

Persist per-claim reporting progress for activity and result comments and field updates, including completion flags and recorded GitHub comment IDs. Give each comment a stable claim/report identifier, distinguishing activity events by repetition and attempt where applicable, so a post that succeeds before its response is lost can be discovered rather than duplicated. Reconcile pending delivery after a restart without launching completed work again, respecting newer human intent while repairing incomplete factory updates. This is a specific durable delivery mechanism within the claim model; a general-purpose outbox remains outside iteration 1.

Use `gh` for board and issue access. `doctor` checks authentication, board fields/options, Docker availability, required repositories/worktrees, selected-suite readiness, the token environment file, and a configurable free-disk-space floor. Check shared readiness before claiming work, and verify selected-suite prerequisites at the pinned `agent-evals` revision before execution. Calibration is an optional suite-maintainer diagnostic, not a factory admission requirement. An unavailable prerequisite creates a visible infrastructure hold: launch no evaluation, record no execution attempt, and consume no recovery retry. Recheck only readiness on subsequent polls so queued work can proceed when the prerequisite becomes available. These checks do not attempt to repair credentials or configuration; explain any required operator action and avoid repeating unchanged diagnostics as issue comments. Apply each hold to the work that depends on the unavailable prerequisite, keeping factory-wide requirements distinct from the selected suite's requirements. Use the actual diagnostic to distinguish a shared failure from a request-specific problem; an absent artifact directory alone is insufficient.

The suite requires a token scoped to its `and-scene` candidate branch and draft-PR operations; keep that separate from board administration credentials. Supply explicit environment paths for launchd, document preventing idle sleep on the Mac mini, and retain the suite's browser-proof setup requirements. Check the free-space floor before admission. On the next successful poll after a reviewed item moves from Review to Done, automatically remove its factory-owned Runner, Skills, and evals worktrees. Keep worktrees while running, waiting, or in Review; a contradictory Done drag during active execution is corrected before cleanup. Record cleanup failures and retry on later polls without blocking other jobs. Results, logs, SQLite history, candidate branches, and PRs remain until manual cleanup. The posted human-review command remains usable until Done; automatic evidence pruning stays outside this iteration.

## Out of Scope

- Issue triage, autonomous fixes, audit-to-issue generation, and new Agent Runner workflows.
- PRs as an alternative eval queue input, labels mirroring factory execution state, and arbitrary workflow-path selection. The template's `eval-request` routing label and red `needs-input` attention label are in scope.
- Automatic sweep expansion, baseline caching/comparison, statistical improvement verdicts, and `inconclusive` classification.
- Evaluating revisions of the `agent-evals` harness or selecting a harness revision in an eval request. Its deployed version is recorded and retained only to preserve the evaluation environment and trace results.
- Implementing the `and-scene` automated-score cutoff. Paul is delivering that separately; a deployed suite that reports completed scores below 40/70 as product failures is an integration prerequisite for factory execution.
- Human evaluation, automatic official scoring or publication, issue closure, PR merging, and automated candidate branch/PR cleanup. Retain recorded candidate links for manual cleanup after human review; do not remove evidence automatically.
- Multiple workers, a hosted database, a remote factory UI, a predictive quota governor, and generalized outbox/cooldown/watermark infrastructure.
- Implementing future work kinds merely because the claim model can accommodate them.
- Dynamic plugin discovery, arbitrary workflow-definition languages, interchangeable databases or queue providers, and additional operating-system service integrations. Reuse is provided through configuration and small work-kind/suite boundaries, not a general plugin platform.
- Additional board-gesture handling, such as treating a completed card dragged back to `Ready` with its old verdict as a fresh request. Use the explicit fresh-request gesture already defined; iteration 1 does not attempt to interpret every board edit.
