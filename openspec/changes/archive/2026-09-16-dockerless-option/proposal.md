## Why

Agent Factory cannot run on the Mac mini today because every attempt, eval or fix, builds and runs a Docker sandbox. The host volume is 228 GiB, each sandbox image build takes several gigabytes, Docker's disk file only shrinks after a manual trim, and Docker Desktop crashed during the last change when the volume filled. An external drive would solve this for Docker, but it has not arrived, and Paul wants the factory fixing bugs before it does.

The two work kinds have different relationships with Docker. Evals need it: the and-scene suite's own `run.sh` launches the container, the suite's provenance records the image ID, and running it on the host would mean changing the suite in `agent-evals`. Fixes are closer to Docker-free: the fix contract (`factory-fix/1`, `fix-outcome.json`) and the fix workflow, which now ships with the factory package, describe behaviour rather than containers, and the Docker-shaped parts of the fix path are the launcher, the container HOME the launcher redirects, the supervisor's container discovery, image cleanup, readiness, and a handful of hardcoded container paths in the workflow. So the useful change is a per-work-kind execution setting: fixes can run directly on the Mac while evals keep the sandbox.

Running on the host gives up the sandbox's fresh filesystem and curated environment. Paul has decided the trade-off explicitly: host-mode fixes run as his user, with his real HOME and CLI logins, in the Runner's autonomous yolo permission mode, with no filesystem boundary. This has a consequence that must be stated honestly rather than papered over: the separate fix token and the PR-only rulesets on `main` remain in place, but on a host where Paul's own GitHub login is available a misbehaving agent can use that login instead, and as an organization owner Paul is not bound by the rulesets. In host mode those two controls are a convention the launcher establishes, not an enforceable boundary. The guards that remain enforceable are trusted-writer admission for the issue text the agent reads, and human merge. Paul accepts this to start, and the setting keeps Docker available for the day the drive arrives.

The handoff from `pickup-and-fix-bugs` also recorded five behaviours Paul observed during review and does not want. They are small, they touch the same operations surface (doctor, status, cleanup, disk accounting, docs), and the disk floor one directly gates host-mode admission, so this change resolves all five rather than leaving them for a follow-up.

The recommendation is **go**. The alternative of waiting for the drive leaves the first real end-to-end proof of the fix path (a real Bug through to a merged PR) blocked on hardware. The alternative of stronger host isolation (a separate macOS user, or `sandbox-exec` profiles) was considered and rejected for now: it adds setup on the mini and design work for a benefit that only matters if the trusted-writer guard fails.

Success means: with `fix.execution = "host"` in the local configuration and Docker Desktop not running, Paul files a Bug and later finds a fix PR, a `needs-input` comment, or an explained failure, exactly as the fix specs already promise; evals remain configured and wait on a clearly reported Docker hold rather than blocking fixes; the resident service behaves the same as an interactive `doctor` says it will; status shows what is live, not the whole history; and evidence stops growing without bound.

## What Changes

- **Per-kind execution setting.** Local TOML gains `fix.execution`, either `docker` (the default, today's behaviour) or `host`. Eval execution accepts only `docker`. The setting is local because it describes the machine, not the deployment; a running attempt keeps the mode it launched with, and the run record stores it.
- **Host launcher for fixes.** In host mode the factory runs the packaged fix workflow directly against the attempt's target clone using the operator's installed Agent Runner and the operator's real HOME. Everything the container start-up script wrote into a throwaway HOME gets a process-local or repo-local equivalent, and nothing user-level is written: git identity, the askpass helper, an empty credential-helper override, disabled terminal prompting, and no URL rewriting or extra headers are applied as process-local git overrides for the launched process rather than edits to a config file the agent can change; role profiles go in the repo-local Runner config as today; the Runner is told not to open a TUI. The fix token never enters the execution plan: the plan carries only the path of the validated private credential copy, exactly as the Docker plan does, and a host-side wrapper reads that file immediately before handing control to the Runner. The Skills plugin bootstrap is skipped: host attempts use the operator's installed codagent plugin rather than re-registering the marketplace from the attempt's Skills clone, which would overwrite the operator's own install. Doctor verifies, rather than writes, that the operator's Runner user settings select the headless backend and yolo permission mode.
- **Workflow staging without user-level writes.** The sandbox publishes the packaged workflow by staging it into the Runner's user-level workflow directory inside the redirected container HOME. On the host that directory is the operator's own. Host mode must supply the packaged workflow to the Runner without leaving files in the operator's Runner configuration: by file path if the Runner supports it, otherwise under an attempt-specific name that is removed at cleanup. The design decides which.
- **Workflow contract: no hardcoded container paths.** The packaged workflow and its outcome scripts hardcode `/artifacts/fix-outcome.json` in several places. The workflow gains an `artifact_dir` parameter that the launcher supplies in both modes (the Docker launcher passes `/artifacts`), and every reference uses it. Because the workflow ships with the factory, this is an in-repo change; whether it is `factory-fix/2` or an optional parameter within contract 1 is a design decision. Host mode requires the revised workflow.
- **Honest provenance for host attempts.** The run record marks the execution mode and records the Runner executable actually used (path and version) and the Runner session directory. The handoff comment on the issue and the attempt evidence state that the attempt ran on the host and that neither the recorded Skills commit nor the recorded Runner commit was the version that executed; the claim still records both commits, and Refs on the card are unchanged.
- **Host Runner session state.** Left to itself the Runner would keep a host session under the operator's `~/.agent-runner/projects/`, outside the artifact root. Instead the factory tells the Runner where to put the session, under the attempt's artifact directory, through a small companion Runner change (a `--session-dir` flag on `agent-runner run`, plumbed to the session-directory option the Runner library already has). The session then sits with the attempt's other evidence, so the supervisor's existing progress sources, evidence inspection, and retention cover it without host-specific path handling. The run record names the directory.
- **Readiness matrix and kind-scoped Docker holds.** Readiness checks are classified as shared, eval-Docker, fix-Docker, or fix-host. Docker on PATH, the Docker daemon, the memory headroom check, the per-run image tag, and the `sandbox-run.sh` launcher-flag checks apply only to kinds that use the sandbox. The runtime's admission path, which today probes Docker memory and runs the shared doctor gate before considering the kind, applies each kind's checks to that kind, and stored readiness holds are reclassified or cleared when the execution mode changes. When fixes run on the host, a Docker problem is an eval-kind hold that leaves fix admission open, and the fix section of doctor reports host-mode readiness instead: the installed Runner executable, `git`, `gh`, `jq`, `python3`, and the validator on the resolved PATH, the selected CLIs authenticated and carrying the codagent plugin, Runner user settings, and the fix token. Supervision of a host attempt is by process ownership alone: no container discovery, no container stop, and no image removal at Done.
- **Service environment matches doctor.** launchd does not inherit an interactive PATH, and the LaunchAgent template sets none, so a host fix could pass `doctor` interactively and fail in the resident service. The template and installation instructions gain an explicit PATH. Doctor reports the PATH it resolved executables against and, when the LaunchAgent definition is installed, checks that the executables host mode needs also resolve on the PATH that definition carries, so an interactive pass cannot hide a service failure.
- **Disk floor that host mode can pass.** The free-space floor becomes per kind: `limits.minimum_free_gib` remains the global default and fixes may set a lower `fix.minimum_free_gib`, since a host fix needs clones and evidence but no image. The selected kind's floor is applied before a slot is reserved. Doctor gains a line reporting Docker's reclaimable space and the trim command, so a floor failure caused by Docker's untrimmed disk file is explained rather than mysterious. The factory never trims Docker itself.
- **Status shows live work.** `agent-factory status` lists only claims that are running, waiting, blocked, held, in Review, or pending a merge sync. Done and superseded claims are omitted unless `--all` is given.
- **Evidence retention.** A configurable retention period (default 14 days) governs evidence for settled claims. Eligibility is stricter than "the card reached Done": the clock starts from a durably recorded Done observation, and pruning happens only while the card is currently Done, no run of the claim is non-terminal or of uncertain ownership, reporting is fully delivered, any required post-merge sync has completed, and clone, worktree, and image cleanup have settled. Expired evidence is removed by cleanup and by a sweep on each tick so history that predates this change is covered. Per work kind, small structured summaries (the fix outcome, eval result JSON, provenance records) are kept and logs, session state, and agent output are pruned; the retained and deletable sets are enumerated in the specs. Pruning records what it removed and any errors. This replaces the eval-execution requirement that artifacts remain until manual cleanup and the iteration-1 promise of no automatic pruning.
- **Doctor prints actions only on failures.** Passing lines no longer carry a repair action, and no line prints an empty one.
- **Documentation.** Installation and operations cover the execution setting, what host mode gives up and keeps, the statement that token separation and rulesets are not enforceable with the operator's login present, the doctor checks host mode needs, the launchd PATH, and the retention setting. `docs/github-setup.md` describes the harness setting as a branch, matching the configuration.

Nothing changes for evals except that Docker problems are reported as an eval-kind hold and their evidence is subject to retention.

## Capabilities

### New Capabilities

None. Host execution is an execution mode of the existing fix capability, not a new behavioural area.

### Modified Capabilities

- `factory-fix-execution`: the sandbox invocation requirement becomes a two-mode execution requirement (`docker` keeps today's behaviour; `host` runs the packaged workflow through the installed Runner with the equivalents above); the workflow contract takes an artifact directory instead of a fixed container path; the credential must never enter the persisted plan in either mode; per-run image tagging and image removal apply only to Docker attempts; the run record and evidence carry the execution mode, the executed Runner, the session directory, and the Skills and Runner provenance caveats; fix evidence retention.
- `factory-fix-reporting`: the handoff comment states the execution mode and provenance caveats for host attempts.
- `factory-eval-execution`: the requirement that artifacts remain until manual cleanup is replaced by the retention rule; suite-owned candidate branches and PRs remain untouched.
- `factory-claim-lifecycle`: readiness holds are classified per the matrix and Docker problems are eval-kind holds when the fix kind runs on the host; the selected kind's disk floor applies before reservation; cleanup gains retention-based evidence pruning with the eligibility rule above and a periodic sweep.
- `factory-operations`: configuration schema (`fix.execution`, `fix.minimum_free_gib`, evidence retention); doctor's fix section in host mode, the readiness matrix, the Docker reclaimable-space line, executable resolution against the service PATH, and no actions on passing lines; the LaunchAgent PATH; status limited to live claims with `--all`; documentation for host mode, its non-enforceable controls, retention, and the branch-based harness setting.

## Technical Approach

The fix launcher already isolates the whole sandbox command line and the bash body run inside the container in one module (`work_kinds/fix/launch.py`). Host mode is a second plan builder behind the same `build_plan` seam: it produces an `ExecutionPlan` whose argv runs a small host wrapper that loads the credential file and process-local git overrides and then execs the installed Runner against the target clone; whose persisted environment holds nothing secret; and whose ownership hints say `sandbox: host` with no image tag. The controller, store, supervisor timers, restart recovery, reconciliation, and reporting stay structurally the same; the fix handler picks the builder from configuration at launch, and the supervisor learns that host plans have no container to discover. The runtime's admission path changes from one global readiness gate to per-kind gates.

Key decisions:

- **Real HOME, no user-level writes.** Paul chose to reuse his real HOME so the CLIs find their logins without copying or linking auth material. The corollary is that the factory must not write anything user-level: git settings are process-local overrides, the askpass script and credential copy live under the attempt's private directory, the Runner profile config is repo-local, the packaged workflow is supplied without leaving files in the operator's Runner configuration, and Runner user settings are checked by doctor rather than rewritten. The Runner session is placed under the attempt's artifact directory by the factory, so nothing accumulates under the operator's `~/.agent-runner/projects/` either.
- **Installed Runner, recorded commit not honoured.** The sandbox builds the Runner from the attempt's source clone. On the host the factory uses the operator's installed `agent-runner` rather than building the recorded clone per attempt, which would add a Go toolchain, build caches, build time, and disk to every attempt. The trade is the same one already accepted for Skills: host attempts record which Runner ran and say plainly that it was not the recorded commit. The Runner clone is still made so the recorded commit is available for evidence and for a later switch back to Docker.
- **Separate fix token, honest about its limits.** The fix credential stays separate from Paul's own login and is pinned into `gh` and git for the launched process. On a host with Paul's own login available this is a convention the agent could defeat, and the documentation and the issue comment say so; the enforceable controls in host mode are trusted-writer admission and human merge. Doctor does not try to prove the operator's login is unavailable, because on Paul's machine it is present by design.
- **Docker becomes a kind concern.** The lifecycle spec already classifies holds as global, kind-specific, or provider-specific. Docker readiness moves from the shared gate to the kinds that use the sandbox, so a host-mode deployment with Docker stopped admits fixes and reports evals as held with the reason.
- **Retention over size caps.** Age-based pruning after a durable Done observation is predictable and explainable in status and doctor; a size cap would delete history depending on how busy the week was. The sweep runs on tick so the existing 2 GB is reclaimed without a manual command, and the eligibility rule keeps it from touching anything a later step still needs.
- **No automatic Docker trim.** Reclaiming Docker's disk file is an operator action with side effects on unrelated images; the factory reports reclaimable space and the command, and stops there.

Material risks: host fixes run yolo as Paul's user on the mini, so a misbehaving agent can touch anything Paul can, including his GitHub login; mitigated only by trusted-writer admission and human merge, and stated plainly in the documentation. Host attempts honour neither the recorded Skills commit nor the recorded Runner commit, which weakens reproducibility of a fix relative to Docker attempts; mitigated by recording what ran and marking every host attempt in evidence and the issue comment. The Runner's user-level settings are shared with Paul's own interactive use, so a change he makes for himself changes the factory's behaviour; mitigated by the doctor check. The resident service runs with a different environment from an interactive shell; mitigated by an explicit PATH in the service definition and a doctor check that reads the installed definition's PATH. Retention pruning deletes evidence, so its eligibility rule, default, and exclusions must be conservative and its sweep must never touch a claim with unsettled work.

## Out of Scope

- Host execution for evals or any change to the and-scene suite.
- Stronger host isolation: a separate macOS user, `sandbox-exec` profiles, or per-attempt CLI configuration directories that would let host attempts honour the recorded Skills commit.
- Building the recorded Runner commit per host attempt.
- Using Paul's default GitHub login for fixes, or a fix-only GitHub App.
- Automatic Docker trimming or image garbage collection beyond the existing per-run image removal.
- The outstanding deployment steps from the previous handoff (fix token, rulesets, shared config replacement, working-clone configuration, caller pins, acceptance reruns); they remain Paul's, and the first real host fix depends on them.

## Impact

- **Code.** `work_kinds/fix/launch.py` (host plan builder, wrapper, workflow supply without user-level writes), `work_kinds/fix/workflow/` (the `artifact_dir` parameter in the workflow and both outcome scripts), `work_kinds/fix/handler.py` and `readiness.py` (mode selection, host readiness, executable checks), `supervisor.py` (skip container discovery for host plans, host session directory as a progress source), `runtime.py` (per-kind readiness gates, per-kind disk floor, hold reclassification), `work_kinds/images.py` (Docker attempts only), `operations.py` (doctor sections and matrix, reclaimable-space line, PATH-aware executable resolution, LaunchAgent template PATH, status filter, no actions on OK lines), `config.py` (new local keys), `store.py` and cleanup paths (Done observation timestamp, retention sweep, pruning record), `cli.py` (`status --all`).
- **Configuration.** New local keys `fix.execution`, `fix.minimum_free_gib`, and an evidence retention setting; `config/local.example.toml` and the LaunchAgent template updated. No shared configuration change.
- **Specs.** Deltas to `factory-fix-execution`, `factory-fix-reporting`, `factory-eval-execution`, `factory-claim-lifecycle`, and `factory-operations`.
- **Docs.** `docs/installation.md`, `docs/operations.md`, `docs/github-setup.md`.
- **Dependencies.** None new. The fix workflow ships with the factory, so the contract change is in this repository. Host mode relies on the operator's installed Agent Runner and CLIs, which Paul already uses interactively; if the Runner cannot run a workflow by file path, supplying the packaged workflow without user-level writes may need a Runner change, which the design will confirm.
- **Users.** Paul, as operator: one new setting to flip, a PATH in the service definition, one doctor section to read, and an explicit acceptance of host-mode risk. Bug authors see the same outcomes, plus a note when a fix ran on the host.
