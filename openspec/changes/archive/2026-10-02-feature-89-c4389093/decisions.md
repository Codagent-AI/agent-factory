| propose | Add a factory-owned task-compliance gate after `implement` and before archive, so `tasks.md` is still at its change path. Run the review after archive in `verify-change`: rejected because that builtin is also outside this repository and the tasks file would have moved. | no |
| propose | A run counts as reviewed only with positive evidence: the validator's own task-compliance review record made after the last implementation commit. Doubt counts as `not-run`. Superseded by PR-2. | Trust the runner's PASS line: rejected because `Status: Passed` does not name gates, and skips are reported as PASS. | no |
| propose | The mechanism for running a missing review is left to design. The proposal recommends an isolated throwaway clone, which has its own empty trust ledger, falling back to a direct re-run. | Direct re-run only: rejected as the recommendation because it still skips on trusted trees until agent-validator#176 is fixed. | propose | A `not-run` or `failed` (violations remain after repair) task-compliance result is a deterministic red item in the PR description. It does not block the PR or change the outcome. | Fail the attempt or withhold the PR: rejected because the issue gives a PR attention item as the example, and the feature spec says review attention never blocks. Let the classifying agent add it: rejected because the item must not depend on agent judgment. | yes |
| propose | `feature-outcome.json` gains an additive `task_compliance` object. The `factory-feature/1` contract, outcome values, and `validator.status` stay unchanged. Superseded by PR-3. | Set `validator.status` to failed when the review was skipped: rejected because that would skip finalization and block the PR. A new contract version: rejected because the field is additive and `verify-feature-outcome.py` checks only the contract and the outcome. | yes |
| propose | Targets that do not declare `task-compliance` in `.validator/config.yml` get a `not-declared` yellow item and no review run. | Red item: rejected because the issue scopes the requirement to declaring repositories. Stay silent: rejected because agent-validator#175 makes an undeclared review a silent no-op that reviewers should be able to see. | no |
| propose | Capabilities: modify `factory-feature-execution` and `factory-feature-reporting`. No new capability. | A new `factory-task-compliance` capability: rejected because the behavior belongs to the existing feature execution and reporting requirements. | no |
| proposal-review | PR-1 applied: a verdict is bound to the head it reviewed. A second gate runs before `classify` and re-reviews whenever the head changed in validated code since the last verdict, which covers simplify, acceptance repairs, and resume merges. After archive, the tasks file is read from the archived change directory and its hash is checked. Commits after the final reviewed head (finalization CI repairs) join the existing orange "commits after acceptance" item, marked as not covered by task-compliance. | Re-review after finalization too: rejected because it would re-enter CI and repeat finalization for small CI fixes. Mark any later commit as red `stale`: rejected because the spec already treats post-acceptance commits as orange, and red on every CI repair would bury real red items. | yes |
| proposal-review | PR-2 applied: the factory records the base itself, from the plan checkpoint, and derives it again on resume. A verdict counts only with proof of the base, the reviewed head and tree, the tasks hash, and a review that ran to a terminal result. Without that proof the factory runs its own targeted review, with option 1 (isolated clone) recommended. | Accept any task-compliance record made after the last implementation commit (the original proposal): rejected because time order does not prove scope, base, or task context. | no |
| proposal-review | PR-3 applied: `validator.status` is `passed` only when a declared task-compliance review passed (or none is declared). It becomes `incomplete` for `not-run` and `review-failed` for `failed`. `validator.checks` keeps the checks-only status. The issue comment that links the PR names any task-compliance result other than `passed`. The outcome stays `pull-request` and the contract name is unchanged, because only scripts in this repository write or read a feature outcome's `validator.status`, and no Python consumer reads it. | Keep `validator.status` unchanged and add only `task_compliance` (the original proposal): rejected because it keeps the misleading pass the issue asks to remove. Use outcome `failed` or bump the contract: rejected because it would block the PR or force handler changes with no consumer that needs them. | yes |
| spec | The verdict's base is the merge base of the reviewed head and the target branch head the attempt started from or last merged, so the reviewed diff is the change the PR carries. This revises PR-2's plan-checkpoint base, and the proposal is updated to match. | Plan checkpoint commit (PR-2): rejected because after a resume merge, the diff from it includes target-branch changes the PR does not carry. | no |
| spec | `factory-feature-execution` adds two requirements, "Gate the feature on a bound task-compliance verdict" and "Qualify the validator status in the feature outcome", and modifies "Classify review attention without blocking" for the red, orange, yellow, and white task-compliance items. `factory-feature-reporting` adds "Report the task-compliance result" rather than rewriting the large annotation requirement. | Modify "Annotate the feature pull request by review attention" and "Comment on feature activity" in place: rejected because the additions are self-contained and copying those blocks invites drift. | no |
| spec | The second gate re-reviews only when the head changed in files the validator gates since the last verdict. The archive commit and changes to ungated files keep the verdict. | Always re-review before classification: rejected because it doubles cost when verification changed nothing that is gated. | no |
| spec | `validator.checks` holds the status of the gates other than the factory's task-compliance gate. `validator.status` is `failed` when the checks failed (unchanged), otherwise `passed`, `incomplete`, or `review-failed` from the task-compliance result. Outcomes written before the gate, such as definition stops, keep their shape. | One combined enum that mixes checks and review failures: rejected because a reviewer needs to know which one failed. | no |
| spec | The issue comment that links the PR names the task-compliance result only when it is not `passed`, and the red count includes the task-compliance item. A passing result adds no text to the comment. | Always name the result: rejected as noise on the common path. | no |
| spec | The review mechanism and whether the validator's retained records can prove the implementation step's verdict are marked deferred-to-design in the execution spec. | Decide in the spec: rejected because the spec skill defers architecture and the issue asks design to surface the choice. | no |
| design | Each factory review runs in a throwaway `git clone --shared` of the head, which has its own git dir and therefore an empty trust ledger, no `validator_logs`, and no one-shot history. It runs `agent-validator review --gate task-compliance --enable-review task-compliance --context-file <tasks> --base-branch <target_head>`, which diffs from the merge base. | A worktree: rejected because it shares the git common dir, and so the ledger. A direct re-run: rejected because it skips on trusted trees and preserves one-shot verdicts. Validating from the task start: rejected because `skip` cannot move the baseline backward. | yes |
| design | The implement step's own task-compliance review is never reused. The factory always runs its own review after implementation. The spec scenario is updated, and the implement step's review remains early repair. | Reuse the validator's review record: rejected because the record names no base, head, tree, or context file, so the binding cannot be proven. | no |
| design | A verdict comes only from review record JSON in the isolated clone: any `fail` gives failed, all `pass` gives passed, `error` retries once and then gives not-run, and no record, `skipped_prior_pass`, or `preserved_one_shot` gives not-run with the console reason. The exit code is ignored. | Use the exit code or the console status: rejected because `review` exits 0 for trusted, no_changes, and no_applicable_gates. | no |
| design | Declaration is read from `agent-validator list` (`Review Gates:` includes disabled reviews). A failure to read it gives not-run. | Parse `.validator/config.yml`: rejected because PyYAML is not available to workflow scripts and the validator resolves its own config. | no |
| design | Gate 1 runs between `implement` and `complete-task`, so repairs belong to the implemented phase. Tasks are hashed with checkboxes normalized, so the checkpoint's tick does not invalidate the verdict. | Run after `complete-task`: rejected because a crash during repair would resume past an unreviewed head. | no |
| design | Re-review is triggered by any change outside `openspec/` since the reviewed head. The spec wording changes from "files the validator gates" to match. | Use `agent-validator detect` to resolve the gated scope: rejected because it adds another format dependency for little gain, since archive and checkpoints touch only `openspec/`. | no |
| design | Repairs use a new `implementor-agent` session, within a loop of at most 3 iterations plus one verification-only run, the same shape as Runner `run-validator`. There is no skip channel, so violations the implementor disagrees with stay and show red. | Allow `update-review skip`: rejected because the factory's verdict must not be waivable by the agent it checks. | no |
| design | `annotate-pr.py` owns the task-compliance items. It removes items with the fixed titles and adds exactly one, and a missing record gives red `no task-compliance record`. It appends the commits after the reviewed head to `Commits after acceptance` as not covered. `record-outcome.sh` takes a new optional `task_compliance` input for the feature contract only. `_pr_message` adds one sentence for not-run or failed. | Let the classifier create the items: rejected because the spec requires deterministic items. | no |
| design | The proposal's note that the workflow is "kept identical under `.agent-runner/workflows/` and src" is corrected: `src/.../workflow/` is the source, and the launcher stages it into the untracked `.agent-runner/workflows/`. | None. | no |
| test-plan | INT-001 runs the real `agent-validator` with a stub reviewer adapter CLI against a claim clone whose head is already trusted, to prove the isolated clone gets past the ledger. It skips, naming the reason, when the validator is missing or its adapter cannot be stubbed. | Stub `agent-validator` only: rejected because it cannot catch the main risk, which is ledger isolation and review-record behavior. Use a real model in CI: rejected for cost and flakiness. | no |
| test-plan | No automated test calls a real model. The acceptance pass may run up to about six real task-compliance dispatches against scratch repositories using the host reviewer CLIs, and must not touch the live service, other claims' clones, or real GitHub issues and PRs. | No real reviews in acceptance: rejected because the real reviewer's record format is the coupling the design depends on. | no |
| test-plan | E2E-001 extends the stub-runner feature cycle to check the issue comment and board outcome for `not-run` and `failed`. Everything else is integration-level. | A full Runner execution of the feature workflow: rejected because the harness has no real Runner and model path, and INT-003 covers the wiring. | no |
| test-plan | Human-only testing: none. | — | no |
| approach-review | RA-001 applied: the base uses the effective target ref. That is `base-merge.json`'s `base_head`, which `prepare-branch`/`merge-base.sh` writes on every resume or continuation, or else `target_head` on a fresh start. It is recorded as `target_ref`. The spec states which target head the base uses and adds a resume-merge scenario. INT-002 now asserts the merged head, not the admission head. | Keep `target_head`: rejected because it is the frozen admission commit, and target-side commits merged on resume would enter the reviewed diff. | no |
| approach-review | RA-002 applied: evidence is gathered from review records in `validator_logs/` and every `previous*/` directory, and from the captured stdout job lines, which survive the validator's auto-clean, including `max_previous_logs: 0`. Preserved-state lines are not dispatches. Failing runs are never auto-cleaned, so violations are always available. A spec scenario covers a pass whose logs were cleaned. INT-001 adds rotating and deleting passing variants with the real validator. | Override `log_dir`/`max_previous_logs` in the isolated clone: rejected because the validator has no environment override, and editing the config there would put it in the reviewed diff. | no |
| approach-review | RA-003 applied: for the feature contract with checks passed, `record-outcome` synthesizes `{result: not-run, reason: no task-compliance record}` when the record is missing or unreadable, so `validator.status` is `incomplete` and `task_compliance` is always present. The spec and INT-004 cover the missing record through the outcome. | Keep the input optional: rejected because it recreates the unqualified pass. | no |
| approach-review | RA-004 applied with a narrower rule: a pass counts only when every changed path outside `openspec/` lies under an entry point whose task-compliance job was dispatched. The spec, design, and INT-002 are updated to match. | Require every changed path including excluded ones (the review's strict reading): rejected because every repository excludes some paths (`.claude`, `.validator`), so most runs would turn red for paths the target chose not to review. Require a root entry point: rejected because it is stricter than needed for full coverage. | yes |
