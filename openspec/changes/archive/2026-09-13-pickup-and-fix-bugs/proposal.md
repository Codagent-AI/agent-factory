## Why

Bugs filed across the Codagent repositories wait until Paul fixes them by hand. Iteration 1 already gives Agent Factory the expensive parts of unattended work: a shared GitHub Project as the queue, durable claims and runs in SQLite, an independent supervisor with timers and restart recovery, and reporting that survives lost GitHub responses. Today that machinery serves only `Eval` requests.

Extending it to bug fixes turns a filed bug into a reviewable pull request, or an explained request for human input, without anyone dispatching an agent. It is also the first real exercise of the claim-lifecycle promise that another work kind can reuse scheduling, persistence, recovery, and reporting without adding kind-specific rules to the core. The Software Factory design note lists this "build phase" as the next step after evals; this change delivers a deliberately small version of it: read the top bug on the board, hand it to an agent, test, open a PR.

The recommendation is **go**. The controller boundary, sandbox, and credential separation exist. What is missing is a headless Agent Runner workflow that fixes an issue end-to-end, a factory work-kind handler that admits bugs, launches that workflow, and reports the result, and the extraction of the work-kind seam that the lifecycle spec promises but the controller does not yet implement. Alternatives were rejected: driving a coding CLI directly from the factory would bypass Agent Runner and duplicate workflow logic; reusing the interactive `simple-change` workflow gives no structured outcome and was not designed for autonomous review steps; LLM triage, confidence thresholds, and daily caps from the original vision add control-plane complexity before there is evidence they are needed.

Success means Paul files a bug in a Codagent repository and later finds one of three things: a PR linked from the issue with the card in Review; a comment explaining why the agent declined the bug and what input it needs, with the card marked `needs-input` until Paul answers in the issue or drags it back to Ready and the factory picks it up again; or an explained technical failure with evidence preserved. Evaluations keep running beside the fix.

## What Changes

- **Bug routing.** The shared routing workflow gains a rule for the bug work kind: an open issue with native Type `Bug` in a configured source repository, authored by someone with write, maintain, or admin access to that repository, is added to the Project with `Owner=factory` and `Status=Ready`. Other authors' bugs enter Backlog without factory ownership, as general work does today. No fenced configuration block is required. A configured bypass marker on the issue at routing time (the `factory-hold` label) routes the bug to Backlog with `Owner=human` so a bug can be filed for tracking only; because the label must be present when the issue is created, each source repository gets a "Bug (tracking only)" issue template that pre-sets it. Routing fires on issue events, so existing bugs are not routed retroactively; they become factory work only when a human sets `Owner=factory` and drags them to Ready.
- **Bug pickup.** The controller selects the top Ready card in the Bug swimlane with `Owner=factory`, in manual board order, re-verifying the author's repository permission at admission. A hand-set field is never sufficient on its own. Bugs carry no per-issue execution overrides; role profiles, branches, and limits come from factory configuration. At admission the factory resolves the target repository, Agent Runner, and Agent Skills branch heads once, records those commits on the claim, and renders them in `Refs` as `target@<7> runner@<7> skills@<7>`.
- **Fix execution.** A new named and versioned headless Agent Runner fix workflow, delivered in `agent-runner` as a companion change, takes a repository, issue number, branch names, and credential location, and produces one of three structured outcomes: a PR reference; a typed `needs-input` decline with reasons; or a typed failure. The workflow composes the existing Runner implementation, validator, and PR sub-workflows rather than adding a second push path. Its prompt instructs the agent to decline rather than guess when a bug is beyond a safe autonomous fix, for example when it stems from a CLI or platform limitation, when several viable solutions need a human choice, when the report lacks reproduction, or when the fix needs a non-trivial specification change and belongs in a Feature. The factory clones the target repository, Runner, and Skills per attempt at the recorded commits from bare mirrors kept under the storage root, and runs the workflow in the existing sandbox under the existing supervisor, restart recovery, and cancellation, with fix-specific inactivity, execution, and total limits.
- **Fix handoff.** The workflow pushes the branch and opens the PR from inside the sandbox as its last step, using a separately configured repository credential. The factory records the PR link, comments on the issue, moves the card to Review, and sets `Verdict=pending-human-review`. A `needs-input` decline leaves the card in Running with the red `needs-input` label, the agent's explanation, and no PR, and frees the fix slot; when a writer comments after the decline, or drags the card to Ready, the factory removes the label and starts a new attempt whose prompt includes the writer comments. Comments from non-writers and from the factory itself are ignored as input, since the repositories are public. After a fix PR merges, the factory updates Paul's working clone of that repository (fetch, update local `main`, refuse a dirty tree, dry-run the merge for conflicts, then merge `main` into the checked-out branch) and closes the issue so the card reaches Done; a dirty tree, diverged local `main`, `main` checked out in another worktree, or a conflict leaves the card in Review with the `needs-input` label and a comment. The PR therefore links its issue without a closing keyword; the factory closes the issue only after a successful sync, never as part of an attempt outcome. A workflow that reports it could not fix the bug, or a red validator, moves the card to Review with `Verdict=failed` and an explanation. Exhausted technical recovery uses `infra-error`. Merge is always human; the factory never closes the issue as part of an attempt outcome and never assigns `passed`.
- **Fresh attempts and idempotent recovery.** Dragging a settled fix card back to Ready requests a new attempt that re-resolves branch heads and retains prior claim and PR history. The technical recovery retry reuses the claim's recorded commits from a fresh clone. Branch names are deterministic per issue and claim, and before any launch or relaunch the factory reconciles the remote branch and open PRs for the issue; when it cannot prove that no side effect occurred, it holds the claim for operator attention rather than launching a duplicate.
- **Per-kind concurrency.** The single global execution slot becomes one slot per work kind: at most one eval attempt and at most one fix attempt at a time, enforced atomically in SQLite through a schema migration. Each attempt builds and runs its sandbox under a per-run image tag passed to the Runner sandbox script, so two concurrent builds from different Runner checkouts never overwrite each other's image and provenance records the image each run actually used. Admission adds a memory headroom check against Docker's memory allowance beside the existing free-disk floor, and the operations documentation states the disk and memory the mini needs to run both kinds. Pause is global; readiness and quota holds are classified as global, kind-specific, or provider-specific in the specification. Fix admission is not bound to the eval night window; it has its own configurable window, defaulting to always open, with a configuration note that the window matters only when a fix role selects Codex.
- **Harness branch for evals.** The `agent-evals` harness stops being pinned to a commit in shared configuration. Evals resolve a configured harness branch (default `main`) to a commit at admission and freeze it on the claim, exactly as they already do for Runner and Skills. Each claim records the harness commit it ran with (on the claim, in Refs, in the frozen-inputs comment, and in the suite's own metadata), so results stay traceable; `doctor` reports an obsolete commit pin rather than ignoring it. This trades cross-night comparability of eval results for convenience: two evals admitted on different days may run on different harness commits, and the recorded commit is what makes that visible. It also means `doctor` no longer proves that a specific harness revision carries the suite features the factory depends on; the suite documentation lists them and the resolved commit is reported.
- **Work-kind extraction.** The controller and runtime currently take eval defaults in the constructor, require `Type=Eval` at admission, write `kind=eval` directly, and construct the and-scene adapter inline. This change extracts the handler protocol, generic unit lifecycle, generic result and presentation contract, and kind-dispatched runtime composition as a behavior-preserving refactor with existing eval tests unchanged, and only then adds the fix handler.
- **Operations.** Configuration, `doctor`, `status`, and documentation cover the fix work kind: target repository mirrors and branches, fix role profiles, fix limits and window, the fix credential file, the bypass marker, and the companion Runner workflow. `doctor` verifies that the companion workflow at the configured Runner branch matches the expected contract version, that the fix credential file is readable and scoped as expected, and that each target repository mirror is reachable. `status` prints which kind holds each slot, why the other is waiting, blocked bugs, and pending merge syncs. Fix limits default to 15 minutes without progress, two hours of execution, and three hours total.

Eval result semantics are not intentionally changed. Evals will share machine resources with a concurrent fix, and the lifecycle requirement of one execution across the service is relaxed to one per kind.

## Capabilities

### New Capabilities
- `factory-routing`: shared route matching, author permission enforcement, precedence between kinds, bypass markers, and one-time initialization for every routed work kind. Eval routing requirements move here from `factory-eval-intake` without behavior change.
- `factory-bug-intake`: bug eligibility, board-order selection within the Bug swimlane, admission re-verification, branch resolution at admission, and the fresh-attempt and unblock gestures for a bug card.
- `factory-fix-execution`: bare mirrors and per-attempt clones at recorded commits, invocation of the versioned fix workflow in the sandbox with configured roles and limits, the workflow's input and outcome contract including the decline outcome, per-run image tagging, evidence retention, and idempotent recovery.
- `factory-fix-reporting`: issue comments, PR linking, the blocked-bug loop, board Status and Verdict updates for a fix, the post-merge working-clone sync, and durable delivery without duplicates.

### Modified Capabilities
- `factory-claim-lifecycle`: replace the global single slot with one atomically enforced slot per work kind; add memory headroom to admission; make the work-kind handler interface concrete; the reconciliation, restart, and cancellation rules apply unchanged to fix runs.
- `factory-eval-intake`: routing requirements move to `factory-routing`; the harness is resolved from a configured branch at admission instead of a deployed commit pin; eval parsing and validation are otherwise unchanged.
- `factory-eval-execution`: the harness revision comes from the claim's resolved commit rather than a configured SHA.
- `factory-operations`: configuration schema, readiness diagnosis, status output, provisioning (fix credential, ruleset, bypass label), resource guidance, and documentation extend to the fix work kind.

## Technical Approach

The fix work kind is the second handler behind the work-kind interface the lifecycle spec reserved. Because the interface exists only in the spec today, the first implementation step is a refactor that moves eval-specific admission, defaults, adapter construction, and result aggregation behind that interface while the existing test suite stays green. The controller keeps owning admission, claims, runs, supervision, reconciliation, and reporting; each handler supplies request interpretation, an execution plan, result interpretation, and report content. No eval concept (repetitions, scores, suites) leaks into the fix handler, and no fix concept leaks into the core.

Key decisions:

- **Branches resolved once per claim.** The fix uses the configured branch (default `main`) of the target repository, Agent Runner, and Agent Skills, resolved to commits at admission and recorded on the claim. The recovery retry reuses those commits; a deliberately fresh attempt re-resolves. The eval harness moves to the same model in this change, so no repository is pinned to a commit in configuration anywhere; every claim records what it resolved. The one enforced containment on the fix credential file is that it holds exactly one repository token variable and nothing else, and the launcher never loads the sandbox script's default secrets file.
- **Clones from local bare mirrors.** Evals cut linked worktrees from three local checkouts, and the read-only Git metadata mounts that make those worktrees work inside Docker live in the eval suite, not in the Runner sandbox script. Fixes target five repositories, only three of which have local checkouts, so the factory keeps a bare mirror per target repository under the storage root, fetches it at admission with the controller's read credential, and clones per attempt from the mirror. The push credential never enters the controller.
- **The workflow owns the fix, the decline, and the PR.** The headless workflow lives in `agent-runner` and is responsible for reading the issue and its comments, deciding whether the bug is safely fixable, implementing with tests, running the validator, pushing the branch, and opening the PR last. The factory contributes nothing LLM-driven and does not inspect the diff. Its contract with the workflow is a small versioned input and a versioned structured outcome; `doctor` checks the contract version, not merely the workflow's presence.
- **Credential model.** This is a deliberate reversal of the design note's isolation decision that the agent phase holds no GitHub credential. The workflow uses a separately configured repository credential inside the sandbox, mirroring the eval suite's arrangement, because the Runner PR steps already exist and a controller-side push path would add code before there is evidence it is needed. The credential reaches the five product repositories rather than a fixture repository, so the change provisions containment: one fine-grained credential with minimal Contents, Pull requests, and Issues scope and no workflow, admin, or Project access, preferably on a machine user; a ruleset on each target repository requiring a pull request for `main` with no bypass for the credential's owner; strict environment allowlisting in the sandbox; and readiness that fails closed on excess scope. Trusted-writer admission, not the sandbox, is the primary trust boundary for the issue text the agent reads.
- **Two slots, one supervisor design.** Concurrency becomes a per-kind count enforced by the run table's unique index, migrated under `user_version`. Each attempt runs under its own independent supervisor process with file-backed output, its own artifact directory, and its own image tag, so restart recovery and container discovery by artifact mount work unchanged.
- **Recovery.** A fix attempt that fails technically gets the existing single recovery retry from a fresh clone at the recorded commits; there is no resume. Reconciliation of the remote branch and open PRs precedes every launch. Cancellation on issue closure and correction of contradictory board drags follow the existing lifecycle rules, extended so that dragging a settled fix card to Ready is a recognized fresh-attempt gesture and a blocked fix card may sit in Running without execution, neither being a contradiction to correct.

Material risks: the issue body and comments are prompt input from any repository writer, mitigated by trusted-writer admission, the scoped credential, the PR-only ruleset, and human merge; two concurrent containers raise disk and memory pressure on the Mac mini, mitigated by per-run image tags, the memory headroom check, the free-disk floor, and documented capacity, with the operator able to pause one kind through configuration; the companion workflow must ship in `agent-runner` before the factory can execute a fix, so rollout is Runner first, factory second, bug routing last; the extraction refactor touches the eval path and must land as its own reviewable step.

## Out of Scope

- LLM triage of incoming issues, confidence thresholds, daily build caps, and a trusted-author list beyond the repository permission check.
- Controller-side diff inspection, prohibited-path checks, or pushing from outside the sandbox.
- Automatic merge, closing the issue as an attempt outcome, or reacting to review comments or CI results on the fix PR after handoff.
- Comparative evaluation of fix PRs, the `pending-eval` PR feeder, and baseline comparison.
- Per-issue execution overrides or a fenced configuration block for bugs.
- More than one concurrent fix, or any second worker machine.
- Cleaning up fix branches or PRs after the card reaches Done.
- A dedicated Blocked column; a blocked bug keeps its column and carries the `needs-input` label.

## Impact

- **agent-factory:** the reusable routing workflow gains the bug rule and bypass marker; a work-kind extraction refactor of the controller and runtime; a new `work_kinds/fix` handler; a schema migration for per-kind slots; bare-mirror management; per-run image tagging and memory admission; configuration, `doctor`, `status`, and docs (installation, github-setup, operations) extend to fix settings, capacity, and the fix credential; the lifecycle, eval-intake, eval-execution, and operations specs are amended and a routing spec is created.
- **agent-runner:** a new named, versioned headless fix workflow with a structured input and outcome contract, composing the existing implementation, validator, and PR sub-workflows, delivered as a companion change and used by the factory from the configured branch.
- **GitHub:** the routing rule for `Bug` issues applies to the five configured Codagent repositories; a `factory-hold` bypass label and a "Bug (tracking only)" issue template are added to each, and the existing `needs-input` label marks blocked bugs; a fine-grained repository credential for fix PRs is provisioned, preferably on a machine user; a ruleset requiring pull requests on `main` is added to each target repository, since none has branch protection today. No new Project fields or Verdict options are required.
- **Operations:** the Mac mini may run an eval and a fix concurrently; the documentation states required free disk and memory; storage gains mirrors and fix runs under the existing root.
